# Evaluation protocol

## 1. Three kinds of results, never mixed

| Kind | Data | Used for | Independent? | Folder |
|---|---|---|---|---|
| **Development** | the 9 development cases; the test-split normals of the corpus; the new-scene check | design decisions, diagnosis | **no** | `results/development/` |
| **Validation** | val_A normals and validation anomalies; stallval; the legitimate-stop validation set; val_B (thresholds only) | checkpoint selection, model selection by pre-registered rules | **no** (they were used to select) | `results/validation/` |
| **Final test** | 228 new runs in the 8 test regions, planned and frozen before simulation, run once | the single independent estimate of DeepDAS Ensemble v1 | **yes**, for DeepDAS Ensemble v1 and the two baselines | `results/final_test/` |

**Rules:**
- No number of one kind is reported as if it were another kind.
- The development 8/9 is a development result.
- The validation macro recall (0.714) is a selection result.
- Only the final-test numbers estimate generalisation.
- After its single evaluation, the final test was used for a diagnosis (study 06). From then on it is **exposed** and is not used as evidence for any later model.

## 2. Thresholds and decisions
- **Thresholds come only from val_B normals.** A threshold is never copied between models.

  | Model | Threshold |
  |---|---|
  | DeepDAS Ensemble v1 | 1.9726181803233118 (ensemble P99) |
  | Supervised single model | −5.523461642265342 (logit P99) |
  | SimStudio Z-score | its shipped threshold 15.392482911229285 |

- **Fewer than 3 windows → no decision.** The unit is reported in the coverage counts, never counted as normal or as detected.
- **Final test.**
  - DL decisions are made **per usable track**, without the oracle vehicle id.
  - A vehicle counts as detected if any of its decided tracks alarms. The truth id is used only for this evaluation step.
  - The Z-score is applied per track as shipped.

## 3. Final-test metrics (pre-registered; `data/processed/final_test/`, `src/deepdas/evaluation/final_test.py`)
**Positives.** The realised injected vehicles of the 9 core types, 105 of 108. Each detector is scored on its decided ones; the **common** variant uses the anomalies decided by all three detectors.

**Negatives:**
- normal driving: the unaffected backgrounds and the normal-scene vehicles;
- legitimate stops, 3 / 5 / 8 s;
- tailgating matched controls.

These three groups are reported separately.

**Metrics:**
- Macro recall over the 9 types, with a bootstrap 95 % CI over runs.
- Pooled recall, precision and F1.
- ROC-AUC and AUPRC (anomalies vs normal driving).
- False-alarm rates per negative group.
- Paired exact McNemar tests on the commonly decided anomalies.
- Decision coverage per group.

**Tables.** T1 per type; T2 overall; T3 stops and tailgating; T4 secondary; T5 uncertainty; T6 focus runs; T7 the Z-score's top features.

## 4. Pre-registration
Every comparison round (studies 03, 04, 05 and 07, and the final test) had a written plan before its simulations or training. The plan fixed:
- the data and its realisation rules;
- the arms and their single difference;
- the selection or replacement rule.

Changes after a plan were made only as **versioned revisions or errata, written before the affected step**. They are kept in the `records/` folders. Frozen artefacts were hash-checked before and after every round.

## 5. Release verification checks (E1–E10)
`scripts/verify_release.py` runs E1–E3 and E9 on any installation. E4–E8 and E10 need either the raw-data package or the original working tree, and are documented in `RELEASE_VERIFICATION.md` with their results.

| Check | What is verified | Pass criterion |
|---|---|---|
| **E1** Manifest | every file of the release against `MANIFEST_SHA256.txt`; the five frozen checkpoints against the hashes recorded when the model was frozen | all hashes equal |
| **E2** Development reproduction | the nine development cases re-scored from the processed data with the frozen models | see §6 |
| **E3** Table reproduction | development tables, validation scores (5 seeds, ensemble, legitimate-stop set) and final-test scores, T1–T7 and vehicle outcomes, regenerated and compared with the shipped `results/`; the shipped `results/` compared with the original project outputs | see §7 |
| **E4** Import | raw runs re-imported with the release code, compared with the shipped processed parquet files | identical data frames |
| **E5** Retraining | the five seeds retrained in an isolated copy (`scripts/train_ensemble.py --threads 1`), compared with the frozen checkpoints and training histories | identical weights (state_dict equal) and histories; **verification only**: the frozen model is never replaced |
| **E6** Generators | sample runs of every generated set regenerated by the release generators | scenario JSON, truth trail and realisation record identical. Excluded from the run record (`run.json`): wall times (`elapsed_s`, `wall_s`), the timestamped export-folder name, and the recorded path of the source scenario, which follows the release layout |
| **E7** Z-score from raw | the shipped Z-score recomputed from raw final-test exports, for a sample | equal to `zscore_scores_precomputed.csv` |
| **E8** Clean installation | fresh virtual environment, `pip install -r requirements.txt`, then `verify_release.py` | all checks pass, with no access to the original project folders |
| **E9** Self-containment and hygiene | no import or path outside the release root; no private absolute paths in code; no conversational or temporary names in the release code (vendored simulator code and archived records excepted) | none found |
| **E10** Originals untouched | hash guard of the frozen model backup and of the original project, before and after the build | 0 differences |

## 6. The E2 criterion (exact definition, version 1.1)
For each of the nine development cases, the unit is the simulated vehicle, as in the shipped development table. The release code recomputes the following from the shipped processed data and the frozen models:
1. the five seed logits and the single-model logit;
2. the per-seed z, z_k = (logit_k − valB_mean_k) / valB_std_k, with the frozen constants;
3. the ensemble score, the mean of the z_k;
4. the decisions.

**E2 passes only if all of these hold:**

| Item | Criterion |
|---|---|
| Per-seed z and ensemble score | \|Δ\| ≤ **1e-5** against the stored reference (the `valid9` rows of the ensemble scores of the selection round) |
| Number of windows per unit | identical |
| Decision of every unit (ALARM / no alarm / no decision), for both units (vehicle, track) and both models | **identical** |
| Thresholds and constants used (ensemble threshold, the five valB_mean / valB_std, the per-seed and single-model thresholds, the checkpoint hashes) | **identical**: read from the frozen files, never recomputed, and checked against the freeze record |
| Summary | 8 of 9 detected by DeepDAS Ensemble v1, 7 of 9 by the single model |
| The development tables (`development_reproduction.csv`, `development_cases.csv`) | **byte-identical** to the shipped files. The single-model logit enters the decision table at its stored 3 decimals |
| Raw seed logits | **reported, not gating** (maximum deviation printed by `verify_release.py`) |

**The tolerance.** It covers float32 accumulation order: different window batching, and another CPU, BLAS or instruction set. A difference within the tolerance that changed any decision would still **fail** E2. No numerical tolerance applies to a decision, a count or a table cell.

**History of the criterion (disclosed).**
- **Version 1.0**, approved before the build, applied the same 1e-5 tolerance to the raw per-seed logits as well.
  - On the build platform (Linux x86-64) it passed: logits 6.7e-6, z 1.2e-6, ensemble 5.9e-7.
  - On the Linux aarch64 (ARM) environment of the clean-install check it **failed** on the raw logits (maximum 1.72e-5). The z (3.4e-6), the ensemble scores (1.6e-6), every decision and the development table were identical within tolerance.
- **Version 1.1**, approved on 2026-10-10 after that result, moved the tolerance to the decision-relevant scores (per-seed z and ensemble score). It added the conditions that every decision and every result table stay identical.
- **What did not change:** the model, its weights, checkpoints, thresholds, normalisation, algorithm and results.
- **The numbers on both architectures** are in `CROSS_PLATFORM.md`.

## 7. The E3 criterion
| File kind | Criterion |
|---|---|
| Result tables: development tables, final-test T1–T7, `FINAL_TEST_REPORT.md` | **byte-identical** on every platform |
| Shipped `results/` against the original project outputs (`results/ORIGINAL_OUTPUTS_SHA256.txt`) | **sha256-identical** |
| Score files: per-seed vehicle scores, ensemble scores, track and vehicle scores, vehicle outcomes | byte-identical on the build platform. On another architecture, a file that is not byte-identical passes only if:<ul><li>rows, keys and column order are identical;</li><li>every decision column (ensemble, single model, per-seed P99/P95, vehicle outcomes), every window count, every label and every other non-score column is identical;</li><li>every per-seed z (stored, or derived from the logits with the frozen constants) and every ensemble score is within 1e-5.</li></ul>Raw logits and single-model logits are reported, not gated |
| `validation_metrics.csv` | every count, recall and rate identical; continuous columns within 1e-5 (on ARM only the recomputed diagnostic P99 differs, by 1.1e-9) |

The comparison is tested against injected changes: a flipped decision, a changed window count, a score off by 2e-5, and a changed table cell each make it fail (`tests/test_verify_comparator.py`).
